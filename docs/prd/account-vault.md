## 1. 背景与目标

### 1.1 背景

用户在 Google、GitHub、Microsoft 等平台各有多个账号（例如 5 个 Google、5 个 GitHub），需要同时管理：

- 每个账号的登录名、密码、2FA；
- 每个账号登录/授权过哪些站点（例如「Google 主账号授权了 X 账号」，以便回溯某个站点到底用哪个账号登录）；
- 备注（恢复邮箱、绑定手机、共享对象、合同到期时间等）。

现有书签与 Skill 模块只解决「资料」和「工具」，没有承载账号凭据的位置。需要一个独立、可控、默认加密的账号库。

### 1.2 目标

1. **一处登记**：账号、密码、2FA、授权关系、备注集中在一个模块内维护。
2. **快速找回**：按平台、名称、账号标识、授权站点搜索，知道「这个站点用的是哪个账号」。
3. **默认安全**：进入账号库需要主密码解锁；密码与 2FA 密钥在浏览器端加密，服务端只存密文。
4. **与现有产品一致**：沿用侧栏、三种布局、分页、设置弹窗、暗色主题与移动端行为。

### 1.3 非目标（首版不做）

- 浏览器扩展、网页表单自动填充；
- 多用户共享账号库与细粒度权限；
- 自动改密、密码轮换编排；
- 自动识别验证码、短信验证；
- 与 1Password / Bitwarden 等第三方密码库双向同步（导入导出见后续迭代）。

## 2. 用户与典型场景

| 场景 | 描述 | 关键能力 |
| --- | --- | --- |
| 多平台多账号 | 5 个 Google、5 个 GitHub，按平台快速切换 | 平台筛选、平台计数、搜索 |
| 登录方式回溯 | 「X 是用哪个 Google 账号登录的？」 | 授权关系、关联账号、登录方式 |

## 3. 术语

- **账号**：某个平台上的一组登录凭据及其附属信息。
- **平台**：Google、GitHub、Microsoft、X 等（首版为自由文本 + 建议值，见待确认问题）。
- **分组**：个人 / 工作 / 客户 / 归档，用于组织账号，不参与权限。
- **授权关系**：一条「该账号在某个站点上的登录身份」记录，可关联账号库中的另一个账号。
- **主密码**：仅用于本机加解密账号库的口令，不上传服务端。
- **解锁会话**：主密码验证成功后，解密密钥仅驻留内存的时间段；自动锁定后清空。

## 5. 信息架构与导航

### 5.1 导航

- 侧栏模块顺序：书签 → Skill → 账号库。
- 账号库模块图标：`KeyRound`；未解锁时在模块行显示锁标记。
- 侧栏分区标题为「标签」，内容与书签的标签区一致：每行是一个平台标签 + 该平台账号数，按数量降序；
- 不提供「全部账号 / 收藏 / 需要处理」等额外快捷视图，避免侧栏层级过深；
- 点击平台标签进入筛选，再次点击或点击筛选横幅的「清除」回到全部账号。

### 5.1.1 模块数据隔离

- 书签、Skill、账号库使用各自独立的数据表与接口，互不读写；
- 账号库不接入书签 / Skill 的标签体系，列表、详情、编辑中均不出现跨模块标签；
- 搜索、筛选、计数只作用于当前模块的数据集，搜索结果不会跨模块；
- 授权关系中的「关联账号」只允许指向账号库内部账号；
- 现有书签与 Skill 仍按产品现状共用标签字典，本次不改动；若后续给账号增加标签，使用独立的 `account_tags` 表，不复用现有 `tags`。

### 5.2 路由

| 路由 | 说明 |
| --- | --- |
| `/accounts` | 账号库列表（默认；未解锁时展示锁定页） |
| `/accounts/:accountID` | 账号详情（未解锁时重定向回列表锁定页） |

新建与编辑使用弹窗，不单独占路由，与书签编辑一致。

### 5.3 页面结构

- 工具栏：侧栏开关、视图（布局 + 可见字段）、搜索、排序、立即锁定、添加账号。
- 内容区：列表 / 卡片 / 表格 + 分页 + 批量操作条。
- 锁定态：工具栏只保留侧栏开关、锁定状态与「解锁账号库」，内容区展示解锁卡片与统计。

## 6. 数据模型

> 字段命名以 SQLite 与现有后端风格为准；所有密文字段均为 Base64 存储的二进制。

### 6.1 `vault_meta`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 固定为 1 |
| `version` | INTEGER | 加密格式版本，首版为 1 |
| `kdf` | TEXT | `argon2id`（或降级 `pbkdf2-sha256`） |
| `kdf_salt` | BLOB | 16 字节随机盐 |
| `kdf_memory` / `kdf_iterations` / `kdf_parallelism` | INTEGER | KDF 参数 |
| `wrapped_dek` | BLOB | 被 KEK 包裹的数据密钥（AES-256-GCM 密文） |
| `wrap_nonce` | BLOB | 包裹 DEK 使用的 12 字节随机 nonce |
| `created_at` / `updated_at` | TEXT | 时间 |

### 6.2 `accounts`

| 字段 | 类型 | 加密 | 说明 |
| --- | --- | --- | --- |
| `id` | INTEGER PK | - | |
| `name` | TEXT | 否 | 显示名称，如「Google 主账号」 |
| `platform` | TEXT | 否 | 平台名，如 Google / GitHub |
| `identifier` | TEXT | 否 | 邮箱、用户名、手机号 |
| `group_id` | INTEGER | 否 | 关联 `account_groups` |
| `login_url` | TEXT | 否 | 登录地址 |
| `login_via_account_id` | INTEGER NULL | 否 | 通过哪个库内账号登录（如 X 通过 Google 主账号） |
| `favorite` | INTEGER | 否 | 0/1 |
| `password_ct` / `password_iv` | BLOB | 是 | 密码密文与 nonce |
| `totp_ct` / `totp_iv` | BLOB | 是 | TOTP JSON 密文：`{secret, issuer, account}` |
| `notes_ct` / `notes_iv` | BLOB | 是 | 备注密文（含换行） |
| `password_updated_at` | TEXT | 否 | 上次改密日期 |
| `last_used_at` | TEXT | 否 | 最近使用时间（首版可只读展示） |
| `created_at` / `updated_at` | TEXT | 否 | 时间 |

### 6.3 `account_groups`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | |
| `name` | TEXT | 个人 / 工作 / 客户 / 归档（可新增） |
| `sort` | INTEGER | 排序 |

### 6.4 `account_authorizations`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | |
| `account_id` | INTEGER | 来源账号 |
| `service` | TEXT | 站点/服务，如 X、Notion、Slack |
| `identifier` | TEXT | 在该站点上的账号标识 |
| `note` | TEXT | 备注，如「用 Google 一键登录」 |
| `linked_account_id` | INTEGER NULL | 关联到库内账号（可空） |
| `status` | TEXT | `active` / `revoked` |
| `granted_at` | TEXT | 授权日期 |
| `created_at` / `updated_at` | TEXT | 时间 |

### 6.5 加密载荷

单字段加密，避免「一行 JSON 全量重写」导致并发覆盖：

- 算法：AES-256-GCM（WebCrypto）；
- nonce：12 字节随机；
- AAD：`v1|account:{id}|field:{password|totp|notes}`；
- 密文与 nonce 分列存储，便于后续轮换格式。

## 7. 安全设计

> 目标不是防御拥有服务器 root 权限的攻击者实时读取内存，而是保证 **数据库、备份、日志、导出文件泄露时，密码与 2FA 不以明文暴露**。

### 7.1 密钥派生与包裹

1. 首次进入账号库：设置主密码（≥ 12 字符，需二次确认；不展示强度评分）。
2. 生成 32 字节随机 DEK（数据密钥）。
3. 用主密码 + 随机盐做 Argon2id（推荐 `m=64MiB, t=3, p=1`）得到 KEK；若运行环境不支持 Argon2，降级 PBKDF2-HMAC-SHA256（≥ 600,000 次）。
4. 用 KEK + AES-GCM 包裹 DEK，保存 `wrapped_dek + wrap_nonce + kdf 参数 + salt`。
5. 解锁时重新派生 KEK，解密 `wrapped_dek`；GCM 校验失败即主密码错误。
6. DEK 只保存在内存（模块级闭包），不写入 `localStorage` / `sessionStorage` / IndexedDB / Cookie。

### 7.1.1 为什么不在服务端加密

用户只需要记住一个主密码：加密用它，解密也用它；没有这个密码就无法解开账号库。区别在于 **密钥在哪一端派生和使用**。

| 方案 | 密钥位置 | 数据库/备份泄露 | 忘记密码 | 使用便利性 |
| --- | --- | --- | --- | --- |
| 客户端加密（本方案） | 只在浏览器内存 | 攻击者只拿到密文，无法解密 | 无法恢复，只能重置 | 每次刷新/超时需要重新解锁 |
| 服务端密钥加密 | 服务端配置/环境变量 | 能拿到服务端配置或 root 的人可直接解密 | 可由服务端重置 | 登录后即可查看，最方便 |
| 不加密 | 无 | 明文直接泄露 | 可重置 | 最方便，也最危险 |

结论：**服务端加密并不比客户端加密更安全**。服务端加密只是把密钥换了个地方存放，一旦数据库、备份、容器环境变量或运维账号泄露，密码会一起暴露；客户端加密让服务端始终只看到密文。代价是忘记主密码不可恢复、切换设备需要重新解锁。

后续如果需要「登录后直接查看」的便利模式，可以在设置中增加「服务端密钥模式」作为显式选项，并在 UI 上标明安全差异；默认仍推荐客户端模式。

### 7.2 解锁会话

- 默认刷新页面即重新锁定；
- 自动锁定：默认 30 分钟无操作，可选 1 / 5 / 15 / 30 / 60 分钟或不锁定；
- 页面隐藏超过自动锁定时间也视为空闲；`beforeunload` 清理内存密钥；
- 退出登录、切换用户、手动点击锁定立即清空 DEK 与已解密缓存；
- 解锁失败不提示具体原因，连续失败增加延迟（0.5s → 1s → 2s，最多 5s）。

### 7.3 复制行为

- 复制密码 / TOTP / 账号后 toast 只显示「已复制」，不显示内容；
- **不实现剪贴板定时清空**：清空会覆盖用户其他复制内容，且浏览器无法可靠控制系统剪贴板；是否清理交给用户或系统剪贴板管理工具；
- 复制密码前可选二次确认（设置项，默认关闭）。

### 7.4 展示与防泄漏

- 列表、卡片、表格默认掩码显示密码；
- 详情页默认掩码，点击「显示」才渲染明文；
- 密码、TOTP 不进入前端日志、错误上报、URL、toast；
- 服务端列表接口只返回明文元数据 + 密文，不返回解密后的内容；
- 列表/卡片/表格上的「显示 / 复制」按需请求详情并解密，解密结果只缓存于内存（建议 60 秒）。

### 7.5 传输与服务端

- 强制 HTTPS（反向代理层）；
- 继承现有 CSRF 中间件与登录态；
- 账号库接口响应加 `Cache-Control: no-store`；
- 服务端不记录请求体；错误日志脱敏；
- SQLite 文件与备份目录权限最小化；
- 主密码错误由客户端判断，服务端不提供「验证主密码」接口，避免额外的离线爆破入口。

### 7.6 TOTP

- 客户端按 RFC 6238 计算：Base32 secret + HMAC-SHA1 + 30 秒步长 + 6 位；
- 允许 ±1 个时间步的时钟偏差；
- 倒计时与动态码每秒刷新，不触发整页重渲染；
- secret、issuer、account 均加密存储。

### 7.7 忘记主密码

- 无法恢复，只能重置账号库（删除所有密文）；
- 重置前必须二次确认并输入登录密码；
- 建议后续提供恢复密钥（离线保存），首版不做。

### 7.8 威胁与缓解

| 威胁 | 缓解 |
| --- | --- |
| 数据库/备份泄露 | 字段级 AES-GCM 加密，DEK 被主密码包裹 |
| XSS 窃取明文 | 严格 CSP、React 默认转义、禁止对密文/明文使用 `dangerouslySetInnerHTML`、依赖审计 |
| 剪贴板残留 | 复制提示、可选二次确认；不做自动清空，需在文档中说明这是系统级限制 |
| 设备丢失/未锁屏 | 自动锁定、手动锁定、刷新即锁定 |
| 恶意浏览器扩展 | 产品无法完全防御，文档中明确提示 |
| 主密码被撞库 | 强制长度、口令质量校验、KDF 成本、解锁失败延迟 |

## 8. API 设计（建议）

> 遵循现有约定：`routes.php` 嵌套路由；写操作使用 `PATCH` / `POST`；错误信息使用普通中文 message（账号库不使用 Skill 的 `[SL-XXX-NNNN]` 错误码）；响应形态按现有 controller 习惯。

### 8.1 账号库元信息

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/vault/meta` | 返回 `initialized`、KDF 参数、salt、wrapped_dek、wrap_nonce；不返回任何账号明文 |
| POST | `/api/vault/setup` | 初始化：保存 KDF 参数、salt、wrapped_dek |
| POST | `/api/vault/change-master` | 更换主密码：提交新的 KDF 参数、salt、wrapped_dek |
| POST | `/api/vault/reset` | 重置账号库：删除 `vault_meta` 与所有密文字段（需登录密码确认） |
| GET | `/api/vault/export` | 导出加密 `.slvault`（含密文与 KDF 元信息） |
| POST | `/api/vault/import` | 导入 `.slvault`（需主密码解密校验后合并/覆盖） |

### 8.2 账号

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/accounts` | 列表：元数据 + 密文（不含明文密码）；支持 `search`、`platform`、`sort`、`order` |
| GET | `/api/accounts/detail?id=` | 详情：元数据 + 密文 + 授权关系 |
| POST | `/api/accounts` | 新建 |
| PATCH | `/api/accounts` | 更新 |
| POST | `/api/accounts/delete` | 删除（支持批量 id） |
| POST | `/api/accounts/authorizations` | 新增/更新授权关系 |
| POST | `/api/accounts/authorizations/delete` | 删除授权关系 |

### 8.3 校验与错误

- `name`、`platform`、`identifier` 必填，trim 后非空；
- `platform` 长度 ≤ 40，`identifier` ≤ 190；
- TOTP secret 若提供，必须为合法 Base32（去除空格与 `=` 后校验）；
- 无效 id 返回 404 语义的中文 message；
- 未初始化账号库时，账号接口返回明确提示「请先设置主密码」；
- 密文字段长度限制与 SQLite 存储上限在实现时确认。

## 9. 前端实现方案

### 9.1 模块注册

## 10. 交互规格

### 10.1 锁定态

- 首次进入：若未初始化，展示「设置主密码」；已初始化则展示「账号库已锁定」。
- 锁定页展示：账号总数、已开启 2FA 数、平台数；主密码输入框与解锁按钮；自动锁定说明。
- 锁定态点击添加、查看、复制、筛选：统一提示「请先解锁账号库」，不出现任何明文。
- 侧栏平台计数可见（仅数量，不含账号内容）。

### 10.2 添加入口

- 工具栏「添加账号」打开弹窗，分四段：
  1. 基础信息：显示名称、平台、账号标识、分组、登录地址；
  2. 凭据与 2FA：密码（显示/隐藏、生成 20 位强密码）、TOTP Secret、发行方；
  3. 授权关系：可添加多行，每行包含站点、站点账号标识、备注、关联库内账号；
  4. 备注。
- 必填校验：显示名称、平台、账号标识；密码允许为空（例如通过第三方登录）。
- 保存后回到列表，新账号按当前排序展示。

### 10.3 编辑

- 列表/卡片/表格操作菜单、详情页「编辑」均可打开同一弹窗；
- 修改密码时更新 `password_updated_at`；未修改则保留原日期；
- 删除需二次确认，提示会同时删除密码、2FA 与授权记录。

### 10.4 详情

- 头部：平台头像、名称、收藏星标、平台徽章、2FA 徽章、待处理徽章；账号标识、分组、授权数量；
- 操作：复制账号、复制密码、编辑、锁定、删除；
- 凭据：
  - 账号标识 + 复制；
  - 密码：掩码/明文、上次修改与年龄、显示/复制；
  - 两步验证：6 位动态码（3+3 分组）、倒计时条与剩余秒数、发行方与账号、复制；
- 授权关系：双列紧凑卡片展示站点、站点账号、备注、授权日期、状态、关联账号入口；点击卡片打开「授权详情」弹窗；「添加授权」使用独立弹窗；卡片区内部滚动并支持筛选，避免大量授权无限向下排；移除授权需二次确认；
- 备注：保留换行，支持编辑；
- 右侧：基本信息（平台、分组、登录地址、登录方式、创建/修改/最近使用）、账号状态（2FA、密码年龄、授权数量）。

### 10.5 一键定位「这个站点用哪个账号」

- 授权关系中的「关联账号」可点击跳转到对应账号详情；
- 账号详情「登录方式」展示 `login_via_account_id` 指向的账号；
- 示例：Google 主账号 → 授权关系「X · @mortal · 关联 X @mortal」；X 账号详情 → 登录方式「Google 主账号」。

### 10.6 空态与异常

- 空账号库：提示「账号库还是空的，先添加第一个账号吧」；
- 平台筛选为空：提示该平台下暂无账号；
- 搜索无结果：沿用现有列表空态；
- 主密码错误：输入框下方错误提示，不泄露细节；
- 解密失败（密文损坏 / 版本不匹配）：提示「无法解密该字段，请检查备份或重新保存」。

### 10.7 响应式

- ≥ 1024px：详情两栏（主内容 2fr + 侧栏 1fr）；
- ≥ 640px：弹窗两列字段；
- < 640px：单列、头部操作按钮仅图标（带 title）、表格横向滚动；
- 暗色主题全部使用语义 token，品牌色仅用于平台头像底色。

## 12. 里程碑与任务拆解

1. **加密与保险库基础**：`vaultCrypto`、TOTP、`vault_meta` 表、初始化/解锁/改密/重置。
2. **后端数据层**：`accounts`、`account_groups`、`account_authorizations` 建表与迁移；CRUD 控制器与路由。
3. **前端模块注册与列表**：`modules.ts`、侧栏、三种布局、搜索/排序/筛选/分页、锁定页。
4. **详情与授权**：凭据、TOTP、授权关系、备注、账号状态。
5. **弹窗与设置**：添加/编辑、密码生成器、设置页、导出/导入。
6. **验证**：加密/TOTP 单测、API 测试、前端构建、移动端与暗色回归。

## 13. 已明确的产品决策

1. 账号库是**顶级模块**，与书签、Skill 并列。
2. 密码采用**主密码 + 客户端加密**，服务端只存密文；进入模块需要解锁。
3. 支持 **TOTP 动态码**；不保存备份码，也不展示密码强度评分。
4. 「授权」= 站点/服务 + 该站点上的账号标识 + 可选关联库内账号 + 备注 + 授权日期，用于回溯「这个站点用哪个账号登录」。
5. 备注为账号的必备字段，支持多行文本。
6. 书签、Skill、账号库三个模块数据完全隔离，搜索与筛选不跨模块；账号库不使用现有标签体系。
7. 侧栏只保留平台标签列表，不提供「全部账号 / 收藏 / 需要处理」等额外快捷视图。
8. 复制密码 / TOTP 只提示「已复制」，不实现剪贴板定时清空。
9. 授权卡片可点击查看详情；新增授权使用独立弹窗，不在详情页内联展开。
10. 可复用 UI 必须组件化；非显而易见逻辑补中文注释。

## 14. 待确认问题

1. **主密码找回**：是否提供一次性恢复密钥？若不提供，忘记即只能重置。
2. **元数据加密范围**：账号名称、账号标识是否也要加密？加密后服务端无法搜索，需要全量解密后前端搜索。
3. **平台字段**：保持自由文本 + 建议值，还是建立平台字典表（含图标、品牌色、登录地址模板）？
4. **授权关系方向**：只从「来源账号」单向记录，还是双向展示（X 账号也能看到「由哪些账号授权」）？
5. **密码历史**：是否需要保留最近 N 次密码与修改时间？
6. **导入来源**：首版是否需要支持 Chrome / 1Password / Bitwarden CSV 导入？还是只支持 `.slvault` 备份？
7. **主密码二次确认**：复制密码前是否默认要求再次输入主密码（更安全但更打断）？
8. **多用户/共享**：未来是否需要把一个账号共享给其他用户，或整个账号库多用户可见？
9. **浏览器扩展**：自动填充是否在路线图中？会影响主机权限与域名匹配模型。
10. **审计日志**：是否需要记录「谁在什么时候查看了密码/2FA」？（单用户场景价值有限）
11. **服务端密钥模式**：是否需要提供「登录后直接查看」的可选模式？该模式会牺牲数据库泄露场景下的安全性。

## 15. 风险

- **XSS 是最大风险**：一旦页面被注入脚本，解锁期间的所有明文都可能被读取；需要 CSP、依赖审计与代码审查。
- **主密码丢失不可恢复**：必须在设置页和首次初始化时明确提示。
- **浏览器扩展**：恶意扩展可读取页面内容，产品无法完全防御，需要文档说明。
- **加密导致搜索受限**：备注/授权备注无法服务端搜索，需在 UI 上明确搜索范围。
- **大规模数据**：全量解密会带来性能与内存压力，首版建议按需解密 + 单账号缓存。
- **TOTP 时钟偏差**：需要容错并提示设备时间不准。
