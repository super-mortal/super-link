## 1. 背景

书签、Skill、账号库三个模块已完整落地，功能层面按各自 PRD 交付。本阶段的重点从「补齐功能」转向「把已交付的部分做扎实」：

- 用户在使用中暴露的体验断点；
- 随功能叠加产生的技术债；
- 安全边界的复核；
- 数据量增长后的性能表现。

本轮讨论来源：实际部署环境（境内服务器、IP + HTTP 访问）中的侧栏高亮异常、页面底部黑边、更新流程与 Skill 安装链路，以及登录页的项目介绍诉求。

## O-1 侧栏模块高亮互斥修复

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认（根因已定位） |
| 优先级 | P1 |
| 影响范围 | 侧栏模块切换 |
| 关联文件 | `frontend/src/components/Sidebar/ModuleSwitcher.tsx` |

- **现状**：`isModuleActive` 对账号库按路由判断，对书签 / Skill 只看 `store.module`。进入 `/accounts` 时点击账号库只做 `navigate`，不会改 `store.module`，该值仍是进入前的模块（默认 `bookmarks`），导致「书签」与「账号库」同时高亮。
- **问题**：两个模块同时呈现选中态，用户无法判断当前所在模块。
- **方案**：先计算唯一的当前模块，再统一比较：

  ```ts
  const activeKey: ModuleKey = isAccountsRoute ? 'accounts' : store.module;
  const isModuleActive = (key: ModuleKey) => key === activeKey;
  ```

  账号库仍按其独立路由高亮；非账号库路由仍按 `store.module` 高亮。
- **验收标准**：
  - 任意路由下侧栏最多一个模块处于 `data-active="true"`；
  - 在 `/accounts` 下只有「账号库」高亮；
  - 从账号库返回列表页后，原模块（书签或 Skill）恢复高亮。
- **风险与取舍**：低风险，仅影响高亮判定，不改变点击与数据加载逻辑。

## O-2 页面底部黑边与根背景修复

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认（根因已定位） |
| 优先级 | P1 |
| 影响范围 | 全站布局、浅色主题 |
| 关联文件 | `frontend/src/index.css`、`frontend/src/layouts/Dashboard.tsx` |

- **现状**：
  1. `index.css` 的 `:root` 仍保留 Vite 模板残留：`color: rgba(255,255,255,.87)`、`background-color: #242424`、`color-scheme: light dark`；
  2. `Dashboard` 中的 `ResizablePanelGroup` 使用 `fixed w-full`，未声明视口高度，高度由内容撑开；内容不足一屏时，`main` 只有内容高度。
- **问题**：浅色主题下页面底部（以及上滑回弹时）露出 `#242424` 深色底，即截图中的黑色横条；移动端 Safari 地址栏收起时同样出现。
- **方案**：
  - 删除 `:root` 中模板残留的 `color` / `background-color` / `color-scheme`，颜色统一由主题 token 控制；
  - 在 base 层增加 `html, body { min-height: 100%; background-color: var(--background); }`；
  - `ResizablePanelGroup` 改为 `fixed inset-0`（或用 `h-svh`），确保面板组始终占满视口；移动端使用 `100dvh` 兼容地址栏变化。
- **验收标准**：
  - 浅色 / 暗色主题下，空列表、登录页、设置页等任意页面均无黑边；
  - 页面上下滚动与移动端回弹时不露出非主题背景；
  - 内容超出一屏时布局与滚动行为与现状一致。
- **风险与取舍**：改动根样式，需回归 `Dashboard`、`Auth`、`Onboarding` 三类布局；`100vh` 与 `100dvh` 需在移动端实测。

## O-3 侧栏展开 / 收起动效

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认（仅侧栏，原型待补） |
| 优先级 | P2 |
| 影响范围 | 桌面端侧栏折叠、移动端抽屉 |
| 关联文件 | `frontend/src/layouts/Dashboard.tsx`、`frontend/src/components/Sidebar/SidebarToggler.tsx`、`frontend/src/components/ui/sidebar.tsx` |

- **现状**：桌面端通过 `panelRef.collapse()` / `panelRef.expand()` 瞬时切换宽度；移动端 `offcanvas` 已有 200ms 过渡。
- **问题**：桌面端展开 / 收起缺少过渡，视觉上生硬。
- **方案**：
  - 方案 A（完整宽度过渡）：折叠时给面板容器加 `transition-[width] duration-200 ease-linear`，拖拽期间临时移除过渡，避免拖拽跟手变慢；
  - 方案 B（推荐先落地）：宽度立即变化，内容区做 150ms `opacity + translate-x` 淡入，规避面板库对宽度动画的限制。
  - 两者都需尊重 `prefers-reduced-motion: reduce`，在该媒体查询下禁用动画。
- **验收标准**：
  - 点击切换按钮后 150–250ms 内完成过渡，无闪烁或跳变；
  - 连续快速点击不抖动、不卡死；
  - 拖拽分隔条时无额外延迟感；
  - 系统开启「减少动态效果」时无动画。
- **风险与取舍**：`react-resizable-panels` 的宽度由内联样式实时控制，方案 A 可能与拖拽冲突，需实测后再定。

## O-4 更新前展示更新日志

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认（仅展示最新版本） |
| 优先级 | P1 |
| 影响范围 | 设置 → 关于、应用更新接口 |
| 关联文件 | `controllers/AppInfoController.php`、`utils/util-functions.php`、`frontend/src/components/Settings/SettingsAbout.tsx`、`frontend/src/store/mainStore.ts`、`frontend/src/store/api.ts` |

- **现状**：`GET /api/app/info` 只返回 `installed_version`、`latest_version`、`update_available`；`fetchAppUpdateInfo()` 仅取 `tag_name` 与 `html_url`，缓存 12 小时。关于页点击「立即更新」直接调用 `POST /api/app/update` 触发 Watchtower，用户看不到本次更新改了什么。
- **问题**：升级属于不可逆操作，用户在不知道变更内容的情况下直接触发更新，缺少决策依据。
- **方案**：
  - 后端在 release 信息中补充 `name`、`body`（更新说明 Markdown）、`published_at`、`html_url`，作为 `latest_release` 一并返回；缓存结构升级，旧缓存缺少新字段时视为过期重新拉取。
  - 只展示最新版本，不新增历史版本接口；需要回溯时通过「查看完整发布页」外链解决。
  - 前端：有更新时展示目标版本号与发布时间；点击「立即更新」先打开「更新内容」弹窗，确认后才调用 `updateApp()`；弹窗内提供「查看完整发布页」外链。
  - 更新说明按 Markdown 渲染，禁止原始 HTML（或使用白名单清洗），链接统一 `target="_blank"` + `rel="noopener noreferrer"`。
  - 降级：GitHub 不可达时显示「暂时无法获取更新说明」，保留发布页链接，更新按钮仍可用。
- **验收标准**：
  - 存在新版本时可看到该版本更新说明，且必须二次确认才会触发更新；
  - 无更新时不展示更新日志入口；
  - 12 小时缓存生效，重复打开设置不重复请求 GitHub；
  - 更新说明中的 `<img onerror>`、`<script>` 等不会执行；
  - 断网 / GitHub 不可达时给出明确降级提示，不阻塞更新入口。
- **更新说明怎么写、怎么显示**：
  - **写入**：发版时推送 `v` 开头的 tag（如 `v0.0.6`），CI 构建镜像；同时在 GitHub 的 Release 页面填写标题与说明（Markdown），这段内容就是 `body`。不需要在仓库里额外维护 changelog 文件。
  - **内容结构建议**：`新增` / `修复` / `优化` / `升级提示` 四段，每段 1–5 条，面向使用者描述行为变化；破坏性变更或需要手动操作的步骤必须写在「升级提示」。
  - **展示**：关于页显示「当前 v0.0.6 → 最新 v0.0.7」与发布时间；点「查看更新内容」打开弹窗，按 Markdown 渲染标题、列表、链接；弹窗底部为「稍后」与「立即更新」。资源链接里的「更新日志」也打开同一弹窗，不再直接跳外链。
  - **缓存与失败**：说明与版本号共用 12 小时缓存；GitHub 不可达时弹窗显示「暂时无法获取更新说明」，只保留发布页链接。
- **风险与取舍**：GitHub API 未认证限流（60 次/小时/IP）；Markdown 渲染需引入依赖（体积与安全成本）；境内服务器访问 GitHub 可能失败，必须做好降级。

## O-5 境内服务器 Skill 安装与更新链路

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认（第一步：可配置前缀 + 错误提示；测试用 HEAD 探测） |
| 优先级 | P1 |
| 影响范围 | Skill 安装、检查更新、应用更新检查、部署文档 |
| 关联文件 | `utils/SkillInstaller.php`、`utils/GitHelper.php`、`utils/util-functions.php`、`frontend/src/components/InstallSkillDialog.tsx`、`Dockerfile.build` |

- **现状**：
  - 服务端执行 `git clone --depth 1 https://github.com/<owner>/<repo>`，超时 60 秒；检查更新执行 `git fetch`，超时 20 秒；
  - 仅允许 `https://github.com` 地址或 `owner/repo` 简写；失败返回 `[SL-IO-0004] git clone 超时`；
  - 容器镜像内已安装 `git`；
  - 应用更新检查访问 `api.github.com`，失败时静默返回 `null`；自动更新由 Watchtower 拉取镜像完成。
- **问题**：境内服务器访问 GitHub 经常超时、连接重置或速度极慢，导致：
  - 「从 GitHub 安装」大概率失败，且错误信息只说明超时，用户不知道如何绕过；
  - 「检查更新」同样失败，Skill 更新能力实质上不可用；
  - 应用更新检查静默失败，关于页永远不提示新版本；
  - Watchtower 拉取 Docker Hub 镜像在境内也可能失败。
- **方案（分层，可分批落地）**：

  **第一步：可配置访问策略 + 错误提示**

  配置项定义（设置页可改，环境变量只作为初始默认值）：

  | 设置项 | 取值 | 默认 | 作用 |
  | --- | --- | --- | --- |
  | 访问策略 `GITHUB_ACCESS_MODE` | `auto` / `proxy` / `direct` | `auto` | `auto`：优先直连，失败后自动改用代理；`proxy`：始终走代理；`direct`：不经过代理 |
  | 代理前缀 `GITHUB_PROXY_PREFIX` | `https://<代理域名>/` | 空 | `auto` / `proxy` 使用；为空时 `auto` 退化为 `direct`，`proxy` 直接报「未配置代理」 |
  | 版本检查 `APP_UPDATE_CHECK` | `true` / `false` | `true` | 关闭后不再请求 `api.github.com`，关于页只显示本地版本 |

  设置页新增「网络」分区（与认证、账号库、集成分区并列）：

  - 三张单选卡片：`自动（推荐）`、`始终使用代理`、`不使用代理`，每项下方写明行为差异；
  - 代理地址输入框 +「测试连接」按钮；测试只对 `https://github.com` 与 `https://codeload.github.com` 发起请求，不测试任意 URL；
  - 保存后写入数据库设置表；环境变量只在首次初始化时作为默认值，UI 保存后以数据库为准；
  - 页面提示影响范围：Skill 安装、Skill 检查更新、应用版本检查；不影响书签 / 账号库接口。

  读取与校验：新增 `Config::getGithubAccessMode()` / `Config::getGithubProxyPrefix()`；代理前缀要求 `https://` 开头、不含用户名 / 密码 / query / fragment，末尾自动补 `/`；非法或非 https 时忽略并写 `error_log`，回退直连，避免配置错误导致应用不可用。

  `auto` 模式的超时策略：直连尝试使用较短超时（建议 10 秒），失败后再走代理（沿用 60 秒 clone 超时），避免用户等待「60 秒 + 60 秒」。

  生效方式（`.git/config` 中始终保留原始 GitHub 地址，换代理或去掉代理都继续可用）：

  - 安装：`git -c url.<prefix>.insteadOf=https://github.com/ clone --depth 1 https://github.com/owner/repo <dest>`
  - 检查更新：`git -C <dest> -c url.<prefix>.insteadOf=https://github.com/ fetch --depth 1 origin`
  - 数据库 `source_url` 永远存原始 GitHub 地址，不存代理地址；
  - 只对 `https://github.com/...` 与 `https://codeload.github.com/...` 两类原始地址生效，其他地址直接拒绝，拼接后再校验一次 scheme 与 host，避免通过前缀绕过白名单（SSRF）。

  效果：

  | 策略 | 代理地址 | 实际行为 |
  | --- | --- | --- |
  | `auto`（默认） | 已配置 | 先直连（10 秒），失败后用代理重试 |
  | `auto` | 未配置 | 与当前版本一致，只直连 |
  | `proxy` | 已配置 | 始终经代理访问 |
  | `proxy` | 未配置 | 直接提示「请先填写代理地址」，不发请求 |
  | `direct` | 任意 | 始终直连，忽略代理地址 |
  | 地址非法 | - | 忽略配置、记录日志、回退直连 |

  部署方式（可选，仅作为初始默认值）：

  ```yaml
  # docker-compose.yml → apache-php.environment
  - GITHUB_ACCESS_MODE=${GITHUB_ACCESS_MODE:-auto}
  - GITHUB_PROXY_PREFIX=${GITHUB_PROXY_PREFIX:-}
  ```

  ```bash
  # .env
  GITHUB_ACCESS_MODE=auto
  GITHUB_PROXY_PREFIX=https://你的代理域名/
  ```

  只影响 Skill 安装 / 更新与应用版本检查，不影响其他接口。第三方公共代理（gh-proxy 一类）只做 URL 前缀转发；因为请求的是公开仓库且不携带任何凭据，风险相对可控，但可用性与隐私不受控，长期使用建议自建代理。

  **第一步同时做：错误信息改造**

  - 区分 DNS 解析失败、连接超时、TLS 证书错误、仓库不存在 / 无权限；
  - 提示中给出可操作建议：配置代理、改用「上传压缩包」、检查服务器网络；
  - 保留现有错误码体系（`SL-IO-0004` 等），只补充可读原因。

  **第二步（v0.0.6 不做）：失败回退**

  `git clone` 失败后尝试通过 `codeload` 下载 zip 并解压到目标目录；该方式没有 `.git`，需将 Skill 标记为「不支持检查更新」，前端「检查更新」置灰并说明原因。本次不实现，后续版本再评估。

  **已确认**：设置页的「测试连接」只做 HEAD 探测，不执行真实 clone；避免测试动作产生目录、耗时过长或触发不必要的仓库下载。

  **其他**

  - 应用更新检查同样支持代理配置或 `APP_UPDATE_CHECK=false`，避免每次请求固定等待 15 秒；
  - 部署文档补充国内网络下的代理建议与 Watchtower 拉镜像说明。
- **验收标准**：
  - 三种策略在设置页可切换并持久化，刷新后仍生效；
  - `auto` 下直连失败会自动改用代理，且总耗时不超过「直连超时 + 代理超时」；
  - `proxy` 未填地址时给出明确提示，不发请求；
  - 配置非法时自动回退直连并记录日志，应用仍可安装（直连）；
  - 未配置代理时，失败信息包含原因与处理建议，而非仅「超时」；
  - 上传 `.zip` 安装路径不受任何影响；
  - 代理配置不能用于请求 GitHub 之外的主机；
  - `APP_UPDATE_CHECK=false` 时，关于页不发起 GitHub 请求。
- **风险与取舍**：公共代理的可用性、隐私与合规性不可控，文档建议自建；zip 回退会失去检查更新能力；`git clone` 超时最长 60 秒，前端需保持明确 loading 状态。

## O-6 登录页重写与项目介绍

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认 |
| 优先级 | P2 |
| 影响范围 | 登录页、认证布局 |
| 关联文件 | `frontend/src/pages/Login.tsx`、`frontend/src/layouts/Auth.tsx` |

- **现状**：`Auth` 布局只有 Logo 与登录卡片；登录页没有项目定位说明，首次访问者（含部署者本人）无法从页面理解这是什么系统。
- **问题**：登录页是公开入口，当前信息密度过低，也不利于部署后自检。
- **方案**：
  - ≥ 1024px 两栏：左侧品牌区（Logo、项目名、一句话定位、4 条能力点），右侧登录卡片；
  - < 1024px 单列：顶部 Logo + 简短介绍，登录卡片在下；
  - 已确认能力点：书签收藏与标签、Skill 管理、账号库（本地加密）、数据自持 / 自托管；
  - 介绍内容围绕「自托管的个人数据管理工具」：书签收藏与标签、Skill 管理、账号库（本地加密）、数据自持、PWA 与暗色主题；
  - 底部展示版本号；不引入营销式文案，不承诺未实现能力。
- **验收标准**：

  - 登录表单、错误提示、跳转逻辑与现状完全一致；

- **风险与取舍**：登录页是公开页面，文案需与备案主体一致；介绍项应随功能变化同步维护。

## O-7 境内部署与 HTTPS 安全提示

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认（仅本人使用，不展示备案号） |
| 优先级 | P1 |
| 影响范围 | 部署文档、登录页安全提示、默认配置 |
| 关联文件 | `README.md`、`frontend/src/pages/Login.tsx`、`frontend/src/components/Settings/SettingsAbout.tsx`、`frontend/src/lib/vaultCrypto.ts`、`frontend/src/lib/copySecret.ts` |

- **现状**：默认通过 `IP:4124`、HTTP 访问；应用内没有备案号展示位；多用户仅在设置内由管理员创建；账号库依赖 WebCrypto 与 Clipboard API。
- **问题**：
  1. 境内服务器上，网站对公网提供 HTTP 服务需完成 ICP 备案，个人主体备案通常仅限非经营性用途；
  2. **非安全上下文下 `crypto.subtle` 与 `navigator.clipboard` 不可用**，账号库的加解密、复制密码、PWA 安装都会失效——截图中的 `http://IP:4124` 正属于该情况；
  3. 缺少「当前访问方式不安全」的提示。
- **前提（已确认）**：该实例**纯自托管、仅本人使用**，不开放注册、不对外提供密码托管服务。因此本项不做经营性备案评估，只解决「个人自用 + 域名备案 + HTTPS」的技术问题。
- **决策（已确认）**：**不做备案号页脚**，也不增加 `SITE_ICP_LICENSE` 之类的展示位；备案与域名配置只写进部署文档。
- **方案**：
  - 部署文档新增「境内部署」章节：备案域名 + HTTPS、公安联网备案、仅个人使用、不开放公开注册；
  - 前端检测 `window.isSecureContext`，为 `false` 时在登录页与账号库给出明确提示：「当前为 HTTP 访问，账号库加密与复制不可用，请使用 HTTPS」；
  - 保持「不支持公开注册 / 多租户」的现状，并在文档中写明：新增用户由管理员在设置中创建。
- **验收标准**：
  - 文档章节包含可执行的备案、HTTPS、公安联网备案步骤与注意事项；
  - HTTP（非安全上下文）访问时，登录页与账号库出现明确提示，而不是加密/复制静默失败；
  - HTTPS 下上述提示不出现，功能正常；
  - 应用内不出现备案号展示位。
- **风险与取舍**：合规结论以当地管局与云厂商审核为准，产品文档只给操作建议，不作法律结论；仅个人自用时风险主要集中在「访问方式是否合规（备案 + HTTPS）」而非服务性质。

## O-9 模块间标签字典完全隔离

| 字段 | 内容 |
| --- | --- |
| 状态 | 已确认（方案 A：同名标签各模块独立） |
| 优先级 | P1 |
| 影响范围 | 书签 / Skill 标签、侧栏、搜索、批量打标签、数据迁移 |
| 关联文件 | `models/Repository.php`、`controllers/Tags*.php`、`controllers/SkillsTagsUpdateController.php`、`store/mainStore.ts`、`components/Sidebar/NavTags.tsx`、`components/Table/Controls/TagSelect.tsx` |

- **现象**：在 Skill 模块新建或使用的标签，会出现在书签模块的侧栏；两个模块的标签列表、数量与批量打标签互相影响。
- **核实结论**：账号库本身没有标签入口（只有平台与分组）；真正共用的是 `tags` 单表——`items_tags` 与 `skills_tags` 都引用同一批 `tag_id`，`/api/tags` 返回全量，前端 `store.tags` 也是全局一份。因此「在账号库加标签」更可能是在 Skill 模块操作后，看到书签侧栏出现了同一个标签。
- **概念对齐**：从用户视角看，账号库的「平台 / 分组」等价于其他模块的「标签」，只是叫法不同。它们存储在 `account_groups` 与 `accounts.platform`，本来就不接入 `tags`；本次隔离保持这一独立字典，不把账号库并入 module 标签体系，也不让书签 / Skill 读取账号库的平台或分组。
- **问题**：违反「书签 / Skill / 账号库完全独立、数据不共用」的产品原则；搜索、筛选、计数与批量操作都会跨模块串数据。
- **方案（推荐 A）**：
  - `tags` 增加 `module TEXT NOT NULL DEFAULT 'bookmarks'`，唯一索引改为 `(module, title, parent)`；
  - 标签创建、更新、删除、查询全部带 `module`；`/api/tags?module=bookmarks|skills`；账号库不接入；
  - 写入 `items_tags` 时校验标签属于 `bookmarks`，写入 `skills_tags` 时校验属于 `skills`；
  - 前端 `store.tags` 拆为按模块获取（或 `fetchTags(module)`），侧栏、批量标签、详情标签选择器只展示当前模块。
- **迁移方案（必须幂等）**：
  1. 新增 `module` 列，历史标签默认 `bookmarks`；
  2. 遍历 `skills_tags`：若某标签被 Skill 引用，则为 `skills` 模块查找同名同父标签，不存在则复制一条（`module='skills'`），把 `skills_tags` 指向新 ID；
  3. 历史书签标签保持 `bookmarks`；重复执行不产生重复标签。
- **验收标准**：
  - 在 Skill 新建标签后，书签侧栏不出现该标签；
  - 书签与 Skill 可各自存在同名标签，互不影响；
  - 搜索、筛选、计数、批量打标签只作用于当前模块；
  - 迁移后原有书签与 Skill 的标签关系不丢失，重复执行迁移结果一致；
  - 账号库仍然不出现标签入口。
- **风险与取舍**：涉及数据迁移与多端点改动，需先备份数据库；若用户其实希望「同名标签跨模块共享」，需要明确否决本项。

  - 展开 / 折叠、搜索、计数、置顶、颜色、编辑、删除入口与现状一致；
